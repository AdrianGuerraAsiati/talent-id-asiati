# Talent ID — Architecture

## 1. Architectural style

Talent ID is a **modular monolith**.

There is one backend application and one primary database, but the codebase is divided into business modules with explicit ownership of data and behavior. This keeps transactions, deployment and operations simple while preserving a path to extract a module later if real scale or organizational pressure appears.

Microservices are intentionally rejected for the first stage. With approximately 50 employees and a small number of reception kiosks, distributed services would add failure modes, deployment overhead, observability cost and duplicated infrastructure without solving a current problem.

## 2. System context

```text
+------------------+                 +----------------------+
| Android Kiosk    | ---- HTTPS ---> | Talent ID API        |
| Reception        |                 | Modular Monolith     |
+------------------+                 +----------+-----------+
                                               |
                        +----------------------+----------------------+
                        |                      |                      |
                        v                      v                      v
                AWS Rekognition         PostgreSQL          Talent Intelligence
                face recognition        Talent ID data      employee source
```

Talent Intelligence remains the source of truth for HR employee data. Talent ID owns attendance, kiosk identity, biometric references, points transactions and reward redemptions.

Talent ID must not read or write Talent Intelligence's database directly. Integration is through a versioned API/webhook contract.

## 3. Business modules

### workforce

Owns the local employee projection required by Talent ID:

- external Talent employee ID;
- active/inactive status;
- display name;
- site assignment;
- schedule reference;
- attendance eligibility.

It is not a second HR system.

### devices

Owns reception kiosk identity and provisioning:

- device registration;
- site binding;
- activation/revocation;
- last-seen timestamp;
- device authentication metadata.

Android devices never contain IAM access keys.

### biometrics

Owns biometric enrollment lifecycle and provider abstraction:

- enrollment status;
- consent/authorization metadata reference;
- provider user reference;
- recognition decision;
- liveness orchestration;
- deletion/re-enrollment.

Raw attendance photographs are transient by default.

The domain depends on a `BiometricProvider` interface. AWS Rekognition is an infrastructure adapter, not a dependency embedded in business logic.

### attendance

Owns attendance facts:

- check-in/check-out;
- site and device;
- method used;
- timestamp;
- recognition confidence;
- manual correction;
- exception/justification;
- derived punctuality status.

Attendance events are immutable facts. Corrections should be explicit adjustments instead of destructive edits.

### rewards

Owns the Talent Points economy:

- point rules;
- point ledger;
- historical points;
- spendable balance;
- reward catalog;
- redemptions;
- approval workflow.

The ledger is authoritative. Cached balances must be derivable from it.

Attendance publishes events; rewards decides whether they generate points. Attendance never writes rewards tables.

### integrations

Owns external contracts:

- Talent Intelligence;
- Odoo if required later;
- notification providers.

It translates external payloads into internal commands and maps internal integration events to external contracts.

### audit

Owns append-only records for sensitive actions:

- biometric enrollment/deletion;
- manual attendance corrections;
- point adjustments;
- device provisioning/revocation;
- administrator actions.

## 4. Dependency rules

Within a module:

```text
api / adapters
      |
      v
application
      |
      v
domain
      ^
      |
infrastructure implements ports
```

Packages may be introduced incrementally. We do not create empty layers merely for appearance.

Cross-module rules:

1. No cross-module ORM relationships.
2. No importing another module's repository implementation.
3. Cross-module references use stable IDs.
4. Synchronous business queries use public application services.
5. Side effects use domain/application events.
6. External events use an outbox before production rollout.
7. Shared code contains technical primitives only, never business rules.

## 5. Persistence

Production persistence is PostgreSQL.

Each module owns its tables. Naming makes ownership explicit:

- `workforce_*`
- `devices_*`
- `biometrics_*`
- `attendance_*`
- `rewards_*`
- `audit_*`
- `integration_*`

Cross-module foreign keys are avoided by default. IDs are UUIDs generated by Talent ID; external identifiers are stored explicitly.

PostgreSQL is preferred because attendance, schedules, points ledgers, reward redemption and reporting are transactional and relational, while the expected data volume is small.

## 6. Online attendance flow

```text
Android camera
   |
   v
POST /v1/kiosk/recognize
   |
   v
devices -> validate kiosk
   |
   v
biometrics -> identify employee
   |
   v
workforce -> validate active employee / schedule
   |
   v
attendance -> append attendance event
   |
   +---- publish EmployeeCheckedIn/Out
                     |
                     v
                  rewards
```

The recognition result is not itself an attendance record. Biometrics identifies; attendance decides and records the business event.

## 7. Talent Intelligence integration

Talent Intelligence is upstream for employee master data.

Preferred contract:

```text
Talent -> Talent ID
employee.created
employee.updated
employee.deactivated
```

Until webhooks are available, a secured sync endpoint or scheduled reconciliation may populate the local workforce projection.

Talent ID exposes attendance and points summaries back to Talent through a versioned API. A shared database is explicitly avoided.

## 8. AWS boundary

Core region: `us-east-2`.

Initial production components:

- one Talent ID backend deployable;
- managed PostgreSQL;
- AWS Rekognition through the biometrics adapter;
- CloudWatch logs and metrics;
- Secrets Manager/SSM;
- KMS where sensitive stored metadata requires encryption.

Face Liveness can use another supported AWS region without changing domain code.

## 9. Android boundary

The kiosk is a client, not a trusted backend.

Responsibilities:

- camera capture;
- kiosk UI;
- secure device-token storage;
- retry/network state;
- local queue for fallback events when offline.

Not allowed:

- embedded IAM credentials;
- direct database writes;
- local authoritative point calculations;
- authoritative attendance state.

## 10. Security and privacy

- Biometric data is treated as sensitive.
- Raw face images are transient by default.
- Enrollment/deletion is auditable.
- Administrative endpoints require strong authentication and authorization.
- Device credentials are revocable per kiosk.
- An alternative attendance method must exist.
- Manual changes require actor, reason and timestamp.
- Logs must never contain raw images or secrets.

## 11. Reliability requirements

Pilot:

- idempotency key for attendance writes;
- duplicate-check window;
- UTC persistence and site-local timezone rules;
- retry-safe external calls;
- structured logs;
- health endpoint.

Before multisite production:

- transactional outbox for integrations;
- backups;
- alarms;
- recovery/runbook tests;
- kiosk revocation procedure.

## 12. When to extract a microservice

A module is extracted only if a concrete pressure exists:

- independent scaling;
- independent release cadence;
- separate team ownership;
- regulatory isolation;
- incompatible workload characteristics.

Until then, the modular monolith remains the default.
